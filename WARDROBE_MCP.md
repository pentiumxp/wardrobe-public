# Wardrobe MCP Wrapper

This document defines the local MCP wrapper for Hermes wardrobe workflows.

## Status

- The MCP server is an adapter layer for Hermes Mobile / agents.
- The Wardrobe Program API remains the authoritative production contract.
- For Hermes Mobile, the MCP server is the required wardrobe entrypoint when mounted; direct Program API calls are not an automatic fallback.
- The MCP server must not read or write SQLite directly.
- The MCP server calls the existing bearer-token Program API with the active owner workspace config and Access Key.
- Hermes Mobile discovers the embedded Wardrobe plugin through `GET /api/v1/hermes/plugin/manifest`. The plugin tab embeds `/?embed=hermes`; model-facing actions still use the `wardrobe` MCP toolset. The embedded UI contract is documented in `docs/MODULES/hermes-plugin.md` and includes `wardrobe.plugin.navigation`, `hermes.plugin.back`, `wardrobe.plugin.back_result`, and `wardrobe.plugin.refresh_required`.
- Wardrobe native AI service is removed. Hermes Mobile owns model execution and
  calls MCP tools for wardrobe data, thumbnails, statistics, and writebacks.
  Wardrobe Web/API endpoints for prompt editing and AI review return
  `410 native_ai_removed`.

## Runtime Boundary

The MCP server runs near the Hermes client, usually as a local stdio subprocess:

```powershell
python scripts\wardrobe-mcp.py --workspace "<active-owner-wardrobe-directory>"
```

Hermes Mobile Gateway profiles should register the server with a fixed owner
workspace and `--no-workspace-override`. Owner-scoped profile registration must
not rely on the model passing a different `workspace` argument at tool-call time.
This keeps each Gateway profile bound to its own `.hermes-wardrobe/access-key.txt`
and `.hermes-cache`.

The MCP runtime is fail-closed by default: tool-call `workspace` arguments are
rejected unless they match the configured `--workspace`, and arbitrary workspace
switching requires the explicit diagnostic flag `--allow-workspace-override`.

Current Hermes Mobile runtime install path:

```text
C:\ProgramData\HermesMobile\gateway-worker\wardrobe-mcp
```

Gateway profile registration is generated by:

```text
C:\ProgramData\HermesMobile\gateway-worker\configure-low-gateways.sh
```

It reads:

- `.hermes-wardrobe/config.json`
- `.hermes-wardrobe/access-key.txt`, or the `access_key_file` named by config
- `.hermes-cache/outfit-context-manifest.json`
- `.hermes-cache/resources/*.json`
- `.hermes-cache/photos/*.jpg`

It never prints, logs, returns, caches, or writes the raw Access Key.

### Mac Production Gateway Registration

Mac production conversations must use the active Home AI Gateway/profile
configuration on Mac production. Registering Wardrobe MCP only in Windows
`lowgw*` development profiles is insufficient for production closure.

The active Mac production Gateway/profile config must preserve existing model
settings and include:

- `toolsets` with `wardrobe`
- `platform_toolsets.api_server` with `wardrobe`
- `mcp_servers.wardrobe` pointing at the Mac production Wardrobe MCP wrapper
- `--workspace <owner-specific Wardrobe workspace root>`
- `--no-workspace-override`

The MCP config may contain only paths, toolset names, and non-sensitive env. It
must not contain raw Access Keys, Gateway API keys, launch tokens, cookies,
session ids, or private inventory dumps.

After every MCP runtime/schema/path change, verify:

- the selected Wardrobe workspace contains `.hermes-wardrobe/config.json` and
  `.hermes-wardrobe/access-key.txt` without printing key contents;
- the active Mac Gateway/profile config contains `wardrobe` in `toolsets`,
  `platform_toolsets.api_server`, and `mcp_servers`;
- direct MCP stdio discovery exposes `wardrobe.sync`;
- selected production Gateway callable schema exposes the expected
  `mcp_wardrobe_*` tools.

If the embedded iframe/proxy works but a model turn says Wardrobe MCP is
missing, inspect this active Hermes Agent/Gateway profile first. Do not start
by debugging the Hermes Mobile frontend or the Wardrobe iframe.

General plugin MCP registration rule for future plugins:

- the plugin project owns its Mac production service, MCP runtime,
  schema/toolset registration, plugin database, plugin secrets, health checks,
  deployment facts, and MCP harness;
- Hermes Mobile owns plugin registry, authorization/provisioning handshake,
  same-origin proxy, iframe launch, postMessage/theme/refresh,
  workspace-switch isolation, and Gateway worker selection;
- production MCP registration must target the actual active Agent/Gateway
  profile, not only a local development profile.

New Hermes Mobile workspaces can be registered with Wardrobe through
`POST /api/v1/hermes/plugin/workspaces`. Hermes generates the workspace Access
Key, sends it once during registration, and Wardrobe stores the token hash plus
owner/workspace binding. The registration response returns only a token prefix
and metadata, never the raw key.

Hermes Mobile onboarding must also install the complete
`wardrobe-style-operations` Skill bundle into the new user's independent Skill
Store. That bundle includes `SKILL.md`, `references/*.md`, and `scripts/*`.
Installing only a short keyless template is insufficient because MCP calls then
work technically but lack wardrobe rules/reference documents. Per-user
credentials still live only in the user's `.hermes-wardrobe` directory and must
not be copied into the Skill.

Hermes Mobile frame embedding is configured per deployment through
`POST /api/v1/hermes/plugin/frame-ancestors`, not by hardcoding any Hermes
domain in Wardrobe. Before rendering the plugin iframe, Hermes should call
`GET /api/v1/hermes/plugin/manifest?origin=<current window.location.origin>`
and use `embedding.requested_frame_ancestor_allowed` to decide whether the
current origin is already allowed. Non-local registered origins must be HTTPS.

After a workspace is registered and bound, Hermes should not send the user to
the legacy Wardrobe username/password form. It should call
`POST /api/v1/hermes/plugin/launch` with the workspace Access Key and
`workspace_id`, then open the iframe using the returned one-time
`entry_path`. Wardrobe consumes that short launch token, creates the owner web
session cookie, and redirects back to `/?embed=hermes&plugin_session=<session_id>`.
The frontend stores that plugin session in `sessionStorage`, removes it from
the visible URL, and sends `X-Wardrobe-Session` on same-origin API calls so
iOS/WebKit iframe deployments do not depend on third-party cookies.

## Cache Ownership

The MCP server owns the owner-local wardrobe cache lifecycle:

- manifest and resource JSON validation
- atomic writes under `.hermes-cache/outfit-context-manifest.json` and `.hermes-cache/resources/`
- first-photo thumbnail validation and writes under `.hermes-cache/photos/`
- stale first-photo thumbnail cleanup
- no-photo item handling
- stale/offline cache reporting

Hermes Mobile should call MCP tools and consume returned metadata, resource
paths, and thumbnail paths. It should not independently write, rename, delete,
or infer freshness from `.hermes-cache` files. If a cache refresh is needed,
Hermes Mobile calls `wardrobe.sync` or `wardrobe.get_primary_thumbnail`.

Program API remains the production truth for data and image bytes. MCP maintains
only the local owner-scoped cache derived from that API.

## MCP Transport

The implementation uses MCP stdio transport:

- JSON-RPC 2.0 messages over stdin/stdout
- UTF-8 JSON
- official MCP `Content-Length` framing for Gateway/SDK clients
- newline-delimited JSON compatibility for legacy direct probes
- stdout contains only MCP messages
- diagnostics go to stderr only

The server exposes the `tools` capability. Streamable HTTP MCP is out of scope for the first implementation.

## Tool Contract

### `wardrobe.sync`

Manifest-first owner cache sync.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "resources": ["optional resource names"],
  "refresh_thumbnails": true
}
```

Behavior:

- Read owner config and Access Key.
- Request `/api/v1/sync/outfit-context/manifest`.
- If the manifest is `304`, validate and reuse local resource files.
- If the manifest is `200`, compare `resources[].checksum` and `resources[].count`.
- Download only changed or missing resources.
- If `resources` limits the sync to a subset, update only those resource files and do not replace the main manifest cache until a full resource sync validates all resources.
- If `refresh_thumbnails` is true, download only missing/changed/invalid first-photo thumbnails listed by `primary_photo_thumbnails`.
- Ignore or remove stale thumbnail files not listed by the current `primary_photo_thumbnails` resource.
- Items with no photos are valid; they are skipped for thumbnail caching.

Output:

```json
{
  "owner": "owner from API",
  "schema_version": 4,
  "manifest_status": 200,
  "changed_resources": ["wear_counts"],
  "resource_files": {"wear_counts": "..."},
  "thumbnail_summary": {
    "listed": 130,
    "downloaded": 1,
    "reused": 129,
    "failed": 0,
    "removed_stale": 0
  }
}
```

### `wardrobe.get_item`

Targeted live item read.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "code": "item code"
}
```

Behavior:

- Calls `GET /api/v1/items/{code}`.
- This is authoritative for current `photos[]`, `primary_photo`, and photo order.
- Use this before current-first-photo visual verification or after photo reorder.

### `wardrobe.search_items`

Targeted item search/list.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "q": "optional query",
  "brand": "optional brand",
  "status": "optional status",
  "loc": "optional inventory location",
  "layer_role": "optional canonical role: Inner | Middle | Outer | Bottom | Footwear | Watch | Accessory | Dress | Home | Bespoke",
  "kind": "wardrobe or watch",
  "limit": 500
}
```

Behavior:

- Calls `GET /api/v1/items` with the given filters.
- This is for targeted resolution, not a replacement for resource sync.
- `layer_role` must use canonical item roles. Use `Footwear`, not `Shoes`; use `Bottom`, not `Pants`.

### `wardrobe.get_primary_thumbnail`

Resolve the current primary thumbnail for one item.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "code": "item code",
  "prefer_cache": true
}
```

Behavior:

- Reads live `GET /api/v1/items/{code}` first.
- If `primary_photo` is null, returns `has_photo=false` without error.
- If the current `primary_photo_thumbnails` resource lists the exact `cache_filename` and the local file is valid, returns the local path.
- Otherwise downloads the safe JPEG thumbnail endpoint and stores it under `.hermes-cache/photos/{cache_filename}`.
- Does not fetch original image bytes.

### `wardrobe.set_primary_photo`

Set one photo as the first product image.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "code": "item code",
  "photo_id": 123,
  "dry_run": true
}
```

Behavior:

- Calls `POST /api/v1/items/{code}/photos/order` with `primary_photo_id`.
- Defaults to dry-run unless explicitly set to `false`.
- Reads back the item after non-dry-run writes.

### `wardrobe.write_history`

Write actual wear history.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "payload": {
    "wear_date": "YYYY-MM-DD",
    "items": [{"code": "item code", "role": "Outer"}]
  },
  "dry_run": true,
  "idempotency_key": "optional stable key"
}
```

Behavior:

- Calls `POST /api/v1/history/outfits`.
- Defaults to dry-run unless explicitly set to `false`.
- `payload.items[].role` must use canonical outfit roles: `Inner`, `Middle`, `Outer`, `Bottom`, `Footwear`, `Accessory`, `Watch`. Do not send `Shoes` or `Pants`.
- Uses Program API idempotency when `idempotency_key` is provided.
- Does not create saved looks unless a documented saved-look endpoint exists.

### `wardrobe.write_item`

Create or update structured item metadata.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "mode": "optional create_only | upsert | replace",
  "payload": {
    "mode": "create_only",
    "item": {"kind": "wardrobe", "code": "item code"}
  },
  "dry_run": true,
  "idempotency_key": "optional stable key"
}
```

Behavior:

- Calls `POST /api/v1/items`.
- Defaults to dry-run unless explicitly set to `false`.
- Top-level `mode` is copied into the Program API payload and overrides `payload.mode`; use `mode: "upsert"` for corrections to an existing item.
- If an existing `code` returns `duplicate_code`, retry this same MCP tool with `mode: "upsert"` when the user intended an update. Do not request generic HTTP or direct Program API fallback for this case.
- `payload.item.layer_role` must use canonical item roles: `Inner`, `Middle`, `Outer`, `Bottom`, `Footwear`, `Watch`, `Accessory`, `Dress`, `Home`, `Bespoke`. Do not send `Shoes` or `Pants`.
- Preserves Program API owner/scope rules.
- Does not perform image recognition.

### `wardrobe.upload_photo`

Upload one local image file to an existing item.

Input:

```json
{
  "workspace": "optional owner wardrobe directory",
  "code": "item code",
  "file_path": "absolute local image path",
  "dry_run": true,
  "replace_photos": false,
  "idempotency_key": "optional stable key"
}
```

Behavior:

- Reads local bytes from `file_path`.
- Calls `POST /api/v1/items/{code}/photos` using raw image body.
- Defaults to dry-run unless explicitly set to `false`.
- Does not accept `file://` strings or path-only uploads in the API payload.

## Statistics Tools

Statistics tools are MCP-side aggregations over the owner-local resource cache.
They exist so Hermes Mobile does not answer dashboard, ranking, wear, photo,
or data-quality questions by issuing many `wardrobe.search_items` /
`wardrobe.get_item` calls and aggregating in the model context.

Statistics tools:

- run `wardrobe.sync` first by default, with `refresh_thumbnails=false`
- refresh only the resources needed by that statistic
- compute from `.hermes-cache/resources/*.json`
- never read SQLite directly
- never fetch original images
- treat no-photo products as valid rows
- cap item samples with `top_n`

Common input fields:

```json
{
  "workspace": "optional owner wardrobe directory",
  "refresh": true,
  "filters": {
    "brand": "optional",
    "owner": "optional",
    "loc": "optional",
    "role": "optional canonical layer_role; use Footwear, not Shoes",
    "channel": "optional",
    "status": "optional",
    "kind": "optional wardrobe | watch",
    "year": 2026
  },
  "group_by": "brand",
  "metric": "count",
  "period": "total",
  "year": 2026,
  "top_n": 20,
  "include_items": false
}
```

Available tools:

- `wardrobe.stats_overview`: compact owner dashboard counts across items,
  watches, featured looks, wear history, photos, maintenance, and data quality.
- `wardrobe.stats_inventory`: wardrobe inventory count/amount grouping by
  brand, owner, loc, role, channel, status, or acquired year.
- `wardrobe.stats_watch`: watch inventory count/amount/wear grouping by brand,
  owner, acquired year, or maintenance level.
- `wardrobe.stats_wear`: wear totals and rankings using `items`,
  `wear_counts`, and `wear_history`. For `period=year` / `year=YYYY`, the
  date basis is `wear_history.wear_date` / `worn_at`, not `acquired_at`.
  `acquired_at` belongs to inventory/acquisition statistics such as
  `stats_inventory`.
- `wardrobe.stats_maintenance`: maintenance threshold state counts and ranked
  due/near-due items.
- `wardrobe.stats_history`: wear-history counts grouped by date, month, city,
  scene, relax value, or temperature band.
- `wardrobe.stats_featured_looks`: featured-look counts and item/brand
  participation.
- `wardrobe.stats_photos`: primary-photo and local thumbnail-cache health,
  including no-photo items, missing cache files, invalid files, and stale files.
- `wardrobe.stats_data_quality`: structured-field quality checks such as
  missing photo, missing material/color/role, missing wear threshold, duplicate
  code, and mixed-language brand buckets.

For broad aggregate requests, Hermes Mobile should call one of these tools
instead of downloading full resources into the chat or looping over individual
items. Use `wardrobe.search_items` / `wardrobe.get_item` only after a statistic
identifies a small target set that needs detailed readback or correction.

Amount metrics use `price_cny` first and fall back to `price_original` when
`price_cny` is empty. A cached item with `price_original` must not be reported
as unpriced only because `price_cny` is blank.
Both fields remain part of the contract, but their value format is canonical:
plain decimal amount strings such as `61400` or `29900.5`, without `¥`, `￥`,
`RMB`, `CNY`, commas, spaces, or `元`.
The original currency is a separate field: `price_original_currency`, using
uppercase currency codes such as `CNY`, `EUR`, `USD`, or `HKD`. Currency must
not be mixed into `price_original` or `price_cny`. Any write with
`price_original` must also provide `price_original_currency`, unless the server
can infer the currency from the original amount text.

Resource checksums include the sync schema version, resource name, and resource
version payload. When a resource output schema changes, bump
`SYNC_SCHEMA_VERSION` so existing owner-local resource caches are invalidated
and refreshed.

Wear statistic semantics:

- `stats_wear(period=year, year=YYYY)` returns items with actual wear records in
  that year, or items whose `wear_year` field is positive when the detailed
  history cache is incomplete.
- The response includes `date_basis: "wear_date"`,
  `wear_year_field_sum`, and `wear_history_count`.
- If `wear_year_field_sum` and `wear_history_count` differ for the selected
  year, the response includes a `wear_year_history_mismatch` warning.

## Error Rules

- Auth failures are reported as auth failures; the tool must not say the key is missing when the API returned 401/403.
- A single missing photo, no-photo item, thumbnail 404, zero-byte thumbnail, or wrong thumbnail MIME is item-level missing visual data, not whole-sync failure.
- Network/API failures may use validated local cache only as stale/offline fallback. Without valid cache, fail closed for recommendations and writebacks. Do not retry the same action through direct Program API as a Hermes Mobile fallback.
- Tool failures are returned as MCP tool results with `isError=true` when the tool was found and invoked.

## Non-Goals

- No direct SQLite access.
- No monolithic bundle sync.
- No all-original-photo cache.
- No owner-specific styling rules in the MCP server.
- No raw secret output.
- No public Streamable HTTP MCP endpoint in the first implementation.
